# Solution design: {{title}}

## Constraints

Identify language, framework, performance, platform, security, scope, and deployment limits.

## Implementation context

List actual source, project docs, patterns, and external documentation with relevance and purpose. Read all relevant context before design. Define what must remain, can change, and must not be touched. Discover exact test, lint, typecheck, and build commands from project configuration.

## Strategy

State the chosen architecture, integration approach, alternatives, and rationale.

## Building blocks

Describe components and distinct responsibilities, diagrams, exact directory maps, interfaces, authentication, request and response structures, errors, data models, schema changes, and integration boundaries. Assign each public requirement to one owner.

## Strategic examples

Use examples only where complex logic needs explanation. Verify SQL names against migrations and trace example rows through conditional branches, NULL, empty results, and zero. Examples do not authorize implementation.

## Runtime view

Describe main flow, validation, data movement, failure classification, recovery, and relevant algorithms. Keep diagrams and names consistent.

## Deployment view

Document environment, configuration, version dependencies, rollout coordination, feature flags, rollback, and migration order as applicable. Planning does not authorize deployment or live infrastructure operations.

## Cross-cutting concepts

Describe security, errors, logging, performance, consistency, distributed tracing, and localization. For UI, include navigation, design-system choices, loading and error states, keyboard behavior, and accessibility targets.

## Approved decisions

Reference closed mission decision IDs. Explain design consequences without maintaining a second editable decision ledger.

## Quality requirements

Give measurable targets and validation methods.

## System acceptance

Translate public criteria to EARS behavior: THE SYSTEM SHALL; WHEN; WHILE; WHERE; or IF/THEN. Cover primary, error, and boundary cases with stable requirement references.

## Risks, debt, and gotchas

Identify current limitations, performance issues, non-obvious dependencies, and evidence gaps without silently expanding task scope.

## Glossary

Define domain, interface, and technical terms used in the document.
